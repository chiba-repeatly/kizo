# KIZO

**記録を、成長に変える。**

筋トレ記録・PFC栄養管理・献立提案・コーチングを統合する、日本語対応フィットネスWebアプリ（開発中）。

## V1.0 scope
筋トレ記録、食事記録、PFC計算、食品検索（出典を明記）、ルールベースの献立・トレーニング提案。初期版はブラウザ内に保存し、GitHub Pagesで公開できる静的Webアプリを目指します。

**Note:** AIチャットコーチ・クラウド同期は将来の開発予定で、現在実装済みではありません。

## V1.0 implementation

日本語・モバイル優先の静的アプリです。実行時ライブラリ、APIキー、ビルド工程は不要です。

- 日別のkcal/PFC、目標・残量、PFC由来のエネルギー比率
- トレーニングの追加・編集・削除、種目別履歴、最高重量、推定1RM、重量推移、月間カレンダー
- 食事の追加・編集・削除、食事区分、グラム換算、出典付き食品検索・手入力
- 残り目標・肉なし設定・時間・予算を使う献立候補、目標・経験・設備・直近2日の記録・疲労による運動候補
- localStorage保存、検証付きJSON入出力、全データ削除、破損・保存失敗時のエラー表示

### Run locally

Node.js 24 と Python 3 を使用します。`npm install` は不要です。

```sh
npm start
```

HTTPサーバーはポート8000で起動します。ES Modulesを利用するため、HTMLを直接ファイルとして開かずHTTP経由でアクセスしてください。表示・記録日は画面上部で変更できます。記録の「編集」を押すとフォームに読み込まれ、日付も変更可能です。編集後は保存、またはキャンセルを選択します。

### Validation

```sh
npm test
node --check app.js
python3 tests/browser-smoke.py
```

`npm test` はNode標準テストのみで、依存追加は不要です。計算、日付別集計、インポート検証、提案条件を検証します。

ブラウザテストにはPython版PlaywrightとChromiumが必要です（今回のクラウド環境には導入済み）。別環境では `python3 -m pip install playwright` と Chromium のインストールが必要です。テストは `/usr/bin/chromium` を使用し、先にポート8000のサーバーを起動します。トレーニング・食事のCRUD、編集時の日付変更、再読込による保持、目標変更、安全な提案、JSON入出力、不正データ拒否、HTML文字列の安全な表示、リセット、破損データ、390px/1440px表示を検証します。専用ブラウザコンテキストで実行し、利用者の記録は変更しません。スクリーンショットは `/tmp/kizo-mobile.png` と `/tmp/kizo-desktop.png` に生成します。

`main` へのpushで `.github/workflows/pages.yml` がテストを実行し、公開用ファイルだけをGitHub Pagesへデプロイします。公開URLは **https://chiba-repeatly.github.io/kizo/** です。

2. GitHubの **Actions → Deploy GitHub Pages** で実行結果を確認します。
3. 初回のPages有効化で権限エラーになった場合は **Settings → Pages → Build and deployment → Source → GitHub Actions** を選択し、失敗した実行を **Re-run all jobs** で再実行します。

ワークフローは標準の `GITHUB_TOKEN` を使用し、有料APIや追加の秘密鍵は不要です。HTML/CSS/JSの参照は相対パスで、プロジェクト配下のPagesに対応しています。公開成果物にはアプリの静的ファイルのみを含め、仕様書・テスト・Gitメタデータは含めません。

### Food data and calculations

限定シードは **USDA FoodData Central, SR Legacy** のパブリックドメインデータから5品のみを掲載しています。[公式データセット](https://fdc.nal.usda.gov/download-datasets/) / [USDAのデータ説明と利用条件](https://fdc.nal.usda.gov/data-documentation.html)。食品は米国の一般食品で、日本の商品・品種・調理条件の実測値ではありません。調理状態と可食部100g当たりの値を明示しています。

| NDB番号 | 食品・状態 | kcal | P g | F g | C g |
| --- | --- | ---: | ---: | ---: | ---: |
| 20045 | Rice, white, long-grain, regular, enriched, cooked | 130 | 2.69 | 0.28 | 28.17 |
| 05064 | Chicken, broilers or fryers, breast, meat only, cooked, roasted | 165 | 31.02 | 3.57 | 0 |
| 01129 | Egg, whole, cooked, hard-boiled | 155 | 12.58 | 10.61 | 1.12 |
| 09040 | Bananas, raw | 89 | 1.09 | 0.33 | 22.84 |
| 11090 | Broccoli, raw | 34 | 2.82 | 0.37 | 6.64 |

値は `100g当たり × 食べた量 ÷ 100` で合計します。画面表示は小数第1位への丸めです。P・Cは4kcal/g、Fは9kcal/gで、比率はこの換算エネルギーの合計を分母とします。ゼロ記録時の比率は0%。食品のkcal欄は出典値を使用するため、PFC換算値とは一致しないことがあります。目標kcalと各マクロ目標は独立して設定できます。出典値を変更した場合は出典欄も更新してください。

献立の順位は各 `abs(max(目標−記録, 0)−候補値) / 目標` をkcal/P/F/Cで合計し、差が小さい順です。献立の価格・時間は参考見積もりで、調味料・加熱による重量変化・地域価格は含みません。運動の推定1RMはEpley式 `重量 × (1 + 回数 / 30)` であり、高回数や自重では特に参考にできません。グラフは重量を記録日順に表示し、日付間隔は等間隔です。

### Privacy and limitations

記録はブラウザの同一オリジン内にのみ保存します。アプリからの外部送信・アクセス解析はありません。外部出典リンクを開く場合やGitHub Pagesの配信におけるアクセスログは各サービスの扱いに従います。localStorageは暗号化された保管庫ではありません。共有端末の利用に注意してください。ブラウザデータの消去・端末やURLの変更では引き継げないため、JSONを定期的に書き出してください。インポートは既存の全記録と目標を置換します。

医療・栄養欠乏の診断やAIチャットは実装していません。提案は小規模なルールベースの候補で、個別の健康状態・アレルギーは評価しません。痛み・体調不良時は運動休止を案内します。アカウント・クラウド同期・AIコーチはV2.0以降の予定です。

### SEO・検索/SNS向け設定

検索用タイトル・説明、Open Graph、Twitterカード、日本語指定、静的HTML内の紹介文、WebApplicationのJSON-LD、SVGファビコンを設定しています。記録データを構造化データやメタ情報に含めることはありません。検索順位・リッチリザルトの表示を保証するものではありません。

公開先URLは **https://chiba-repeatly.github.io/kizo/** に統一しました。canonical・og:url・JSON-LDのurl・sitemap.xmlはこのURLを指定し、SNS共有画像は `assets/social-card.png`（1200×630）を絶対URLで参照します。元デザインは `assets/social-card.svg` です。

これは公開先の設定であり、実際のデプロイ完了を示すものではありません。PRのマージ後、上記GitHub Actionsの実行結果と、公開URL、`sitemap.xml`、`assets/social-card.png` のHTTP応答を確認してください。独自ドメインへ変更する場合は、これらのURLをまとめて変更します。

### 楽しむための重量比較・継続称号

ダッシュボードに選択日の総重量（入力重量×回数×セット）と動物・物へのたとえを表示し、個々の記録には1回の入力重量のたとえを表示します。総重量は同時に挙げた重量ではありません。比較基準は演出用に定めた目安（水1L=1kg、ネコ4kg、イヌ20kg、パンダ100kg、小型車1,000kg、ゾウ5,000kg）で、生物学的な平均値や特定車種の仕様ではありません。実際の重量には幅があります。自重分は入力重量に含めず、重量0の記録にはその旨を表示します。

称号は表示日以前にトレーニングを記録した日数で計算します。同日の複数種目は1日、自重の記録も1日です。1日「はじめの一歩」、3日「エンジン始動」、7日「コツコツ戦士」、14日「パワーヒーロー」、30日「ハルク級」、60日「継続のレジェンド」。筋力や健康の評価ではなく、連続日数や重量を競わせる機能でもありません。編集・削除・インポート後は記録から再計算し、称号専用の個人データを追加保存しません。公式キャラクターの画像・ロゴは使用していません。

### 称号図鑑：8ジャンル・115種類

上記の基本継続レベルに加えて、称号図鑑から獲得済みの称号を選んで飾れます。ジャンル・獲得済み/未獲得で絞り込みでき、各称号に条件と進捗を表示します。

| ジャンル | 種類 | 条件の例 |
| --- | ---: | --- |
| 継続 | 24 | 記録日数1〜1,000日（非連続） |
| 部位 | 48 | 胸・背中・脚・肩・腕・体幹それぞれ1〜200記録日 |
| 種目探検 | 10 | 異なる種目名2〜30種類 |
| 自重 | 8 | 重量0kgの記録がある日1〜100日 |
| 食事 | 10 | 食事記録日1〜200日 |
| 両立 | 8 | 運動・食事を両方記録した日1〜200日 |
| おかえり | 4 | 記録間隔が7日以上空いた後の記録日1〜14回 |
| バックアップ | 3 | JSON書き出し操作1・3・10回 |

種目名はUnicode NFKC正規化・前後空白除去・英字大小文字の統一を行いますが、同義語の統合は行いません。種目名を変えるだけで種類数が増える可能性がある、自己記録向けの遊びです。「おかえり」は実際の休養を推測しません。食事称号も食事の量・質や栄養の充足を判定しません。

記録由来の獲得状況は表示日以前のデータから計算し、バックアップ操作回数のみ全期間です。選択は `selectedTitle`、書き出し操作回数は `exportCount` として既存version 1 JSONに任意フィールドで保存します。古いJSONも読み込め、存在しないフィールドは未選択・0回として扱います。インポートはこれらも置換します。削除等で選択中の条件を満たさなくなると表示を自動で切り替えます。書き出し操作は端末への保存成功を保証しません。

`python3 tests/browser-titles.py` で図鑑・選択保存・JSON書き出し・リセット・モバイル表示を検証できます（先に `npm start`）。

## トレーニング改善版（PR用・未公開）

### ジムでの使い方

`#training` を開くと、紹介文・ダッシュボード・称号図鑑を畳み、記録日・今日の種目・完了操作を優先して表示します。種目を追加すると未完了の予定が保存され、セットごとに重量と回数を変更して「完了」を押せます。入力値は変更確定時に保存します。記録の追加・セットのコピーだけでは、総重量・履歴・称号・最近のトレーニング判定に入りません。

- **前回コピー**：選択日より前の直近の記録日にある、同じ種目名の完了セットを未完了としてコピーします。英数字の全角・半角、前後空白、英字大小文字は正規化します。同義語は統合しません。入力済みセットの置換には確認を挟みます。
- **セット操作**：追加・直前や任意セットのコピー・重量/回数の変更・完了/未完了の切り替え・削除に対応します。最後のセットの削除は種目自体の削除として確認します。1種目100セットまでです。
- **メニュー**：手入力または今日の種目からテンプレートを作り、種目・各セットの値を編集し、種目を並び替えできます。テンプレートは100件、各50種目までです。名前が同じテンプレートの作成や、当日に同じ種目がある場合の追加は止めて、既存データを保護します。
- **休憩**：60/90/120秒と任意の1〜3,600秒。自動開始・終了音は初期状態で無効です。時間設定の変更は次回開始時に反映します。一時停止・再開・リセットができ、実時刻の終了予定を保存するため、画面移動・再読込・バックグラウンド復帰でも時刻から残り時間を求めます。ブラウザや端末の省電力制御により背景での終了音・通知は保証しません。通知権限は要求しません。端末の時計を変更すると残り時間に影響します。
- **成長表示**：完了セットだけで最高重量、同じ重量での最高回数、日別の総重量、前回との差を計算します。同一重量・同一セット数の比較では合計回数の差を示し、条件が違う場合は成長と断定しません。推定1RMはEpley式を使い、重量あり・12回以下のセットのみ対象です。自重種目は合計回数のグラフと表を表示します。
- **終了時**：「今日のトレーニングを振り返る」で完了セット数・未完了数・重量のたとえ・現在の称号を確認できます。これ自体が未完了セットを完了させることはありません。重量は自重・マシンの力学を含まない入力値です。同じ種目で入力方法を揃えてください。

### 保存形式と安全な移行

製品名のV1.0と、JSONのスキーマ番号は別です。この改善版はスキーマ **version 2** を使用します。

1. 現行の `kizo.v2` があれば検証して読み込みます。破損していても旧データへ勝手に戻しません。
2. `kizo.v2` がなく旧 `kizo.v1` があれば、まず旧データを検証します。
3. 旧形式の `weight × reps × sets` を同じ重量・回数のセット配列に展開し、すべて完了済みにします。元データ、食事、目標、選択称号、書き出し回数を保ちます。
4. 検証が通ってから、移行前の文字列を `kizo.pre-v2` に退避し、別キー `kizo.v2` に新形式を書きます。元の `kizo.v1` と既存の退避データは上書きしません。
5. 容量不足・破損・移行失敗時は元データを保持し、通常の保存を停止します。設定の **「移行前のデータを書き出す」** で元JSONを退避できます。移行前データがない場合、手元のバックアップを使用してください。

新JSONにはセットの完了状態、テンプレート、タイマー状態・設定も含まれます。旧version 1と新version 2のJSONを読み込めますが、読込は現在の全データを置換するため確認が必要です。新形式を旧アプリへ読み込ませることはできません。元データと退避データのため追加のlocalStorage容量が必要です。全削除を選択すると、移行前の元データ・退避データも削除します。事前にJSONを保存してください。

### 検証の再実行

```sh
npm test
node --check app.js
node --check training-ui.js
python3 -m pip install -r tests/requirements.txt
python3 -m playwright install --with-deps chromium
# 別ターミナルで npm start を実行後:
python3 tests/browser-smoke.py
python3 tests/browser-titles.py
python3 tests/browser-training.py
```

PythonのPlaywrightはテスト専用で、アプリの実行依存は追加していません。`/usr/bin/chromium` があれば利用し、それ以外はPlaywright管理のChromiumを使います。`KIZO_CHROMIUM` で実行ファイルを指定できます。スクリーンショットは既定で `/workspace/artifacts`、`KIZO_ARTIFACTS` を指定した場合はそのディレクトリへ保存します。専用のブラウザコンテキストと検証用データを使います。

GitHub Actionsにも同じ3本のブラウザテストを追加し、PRで再検証できるようにしています。CIでの成功は各実行結果を確認してください。公開ワークフローには `training-model.js`、`training-ui.js`、`storage.js` を含めていますが、この作業ではmainへの反映や本番公開を実施しません。
